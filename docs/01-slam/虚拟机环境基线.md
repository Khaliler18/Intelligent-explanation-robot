# SLAM 虚拟机环境基线

适用于 [A 线：本地仿真验证 TODO](本地仿真验证TODO.md) 与 [B 线：实机建图 TODO](实机建图TODO.md)。统一方案为 Ubuntu 22.04 LTS 虚拟机 + ROS 2 Humble + GLIM（ROS 2 包名 **`glim_ros`**，不是文档中常见的 `glim_ros2`）+ MID-360，采用 CPU 模式。

本文件规定**要求值**；电脑 A 的**实际部署值**、逐项键值、相对本基线的偏差与校验记录见 [SLAM A 虚拟机环境](SLAM_A虚拟机环境.md)。电脑 B 由该环境的**镜像**部署，实测值应与之一致——需要逐项对照时以该文件为准。

采用“一份标准模板，部署两份虚拟机”的方式。电脑 A、B 均安装 GLIM、雷达驱动、SDK 和全部基线工具，不因工作线不同而省略组件。

- 确定并记录统一虚拟机平台、系统镜像、资源与网络配置。
- 在标准模板中安装 Humble、GLIM（`ros-humble-glim`、`ros-humble-glim-ros`）、MID-360 驱动、SDK、RViz2、rosbag2 及编译工具。
- 按 [GLIM 安装文档](https://koide3.github.io/glim/installation.html) 的 PPA 方式固定依赖版本与 CPU 模块，验证节点与查看器启动。
- 整理环境清单、apt 软件包版本、依赖来源地址、编译选项、目录和配置文件校验值。
- 关闭标准模板后导出虚拟机镜像，记录基线编号与镜像 SHA-256；由同一镜像部署电脑 A、B。
- 核对两台的资源、系统、软件版本和配置文件，登记唯一实例标识及宿主机网卡映射。
- 在两台保存同名基线快照；基线变更时统一更新模板、清单和两台虚拟机，不单独升级依赖。

验收：两台均能启动 GLIM 与查看器，统一配置项完全一致，允许不同的部署参数有记录。

基线验收后，两条线可分别开展示例验证与设备接入。

## 环境一致性如何保证

**由同一模板镜像保证，不要求用示例数据做两机交叉验证。**

基线原先要求"B 线正式区域采集前，两台电脑必须通过 A 线的相同示例交叉验证"。该要求写在"两台各自手工配置"的前提下——当时环境必然存在细微差异，只能靠示例数据反向验证。

改为"一份模板镜像部署两台"之后（见 [SLAM A 虚拟机环境](SLAM_A虚拟机环境.md) 第九节），软件版本、配置与路径已**逐字节相同**。再用几十 GB 示例数据去验证一件已由镜像保证的事，属重复劳动，且代价不低（下载两份、传输一份、两台各跑一遍、比对日志与轨迹）。

### 镜像能保证的

操作系统文件、全部 apt 包版本、配置文件与环境变量（`.bashrc`、`RMW_IMPLEMENTATION`、`ROS_DOMAIN_ID`）、软件源列表、目录布局、内核版本。

### 镜像保证不了的

- **宿主机差异**：CPU、磁盘、GPU 不同，同一份数据跑出的**耗时与峰值内存**会不同。基线本就要求"运行耗时单独记录"，这是已知条件，不是缺陷。
- **B 机是否按部署文档正确部署**：宿主机虚拟化预处理、主机名、`/etc/machine-id`、桥接网卡映射都在宿主机或客户机内部，镜像带不过去。**B 机须按交付包内[部署文档](../../B环境/部署文档.md)逐条自查**——这是部署验收，不是等价性证明。
- **部署之后的维护**：任一台单独升级依赖即造成分叉。基线变更时必须统一更新模板、清单和两台虚拟机。

### 两点必须记住

1. **「软件环境相同」不等于「运行结果相同」。** 多线程优化本身存在非确定性，即使同一台机器重复处理同一数据也可能出现细微差异。因此数值比对一律按预先记录的容差进行，**不要求浮点输出逐字节一致**。
2. **两条线各自验证的内容不同**：A 线在电脑 A 上用公开示例验证 GLIM 方案可行、流程可复现（A1、A2）；B 线自采数据须能在电脑 A 复现（A3），这是跨机数据重建的验证，与两机等价性无关。

## 宿主机前提

两台宿主机都必须**不加载 Windows 虚拟机监控程序（Hyper-V）**，否则 VMware Workstation 无法使用硬件虚拟化，只能退到用户态监控器 `Monitor Mode: ULM`，CPU 与磁盘 I/O 慢一个数量级，且 **vCPU 越多越严重**。

2026-10-13 电脑 A 因此出现 Ubuntu 安装器长时间无响应，且一次表面"安装完成"之后虚拟磁盘仍为创建时的 13172736 字节、**一个字节都未写入**。

- **判断方法**：查看虚拟机目录下 `vmware.log` 中的 `Monitor Mode:` 行，出现 `ULM` 即为降级模式。更硬的判据是 `\Hyper-V Hypervisor Logical Processor(*)\Total Run Time` 性能计数器——能取到 `hv lp` 实例就说明 hypervisor 在运行。
- **2026-10-13 电脑 A 实际执行的处理**（按此顺序，每步后重启）：
  1. Windows 设置 → 系统 → 高级 → 虚拟工作区 → 关闭「**虚拟机平台**」与「**Windows 虚拟机监控程序平台**」
  2. 管理员终端执行 `bcdedit /set hypervisorlaunchtype off`
  3. 注册表关闭 VBS：`DeviceGuard\EnableVirtualizationBasedSecurity` 置为 `0`、`DeviceGuard\Scenarios\SystemGuard\Enabled` 置为 `0`
  4. 虚拟机设置 → 选项 → 高级 → 勾选「**为启用了 Hyper-V 的主机禁用侧通道缓解**」（对应 `.vmx` 中的 `ulm.disableMitigations = "TRUE"`）
- **注意**：仅仅关闭「内核隔离 / 内存完整性」无效。即使 `HypervisorEnforcedCodeIntegrity\Enabled` 为 `0`，只要 `EnableVirtualizationBasedSecurity` 仍为 `1`、或 `hypervisorlaunchtype` 未设为 `Off`，hypervisor 依旧会在开机时加载。
- **重要经验**：上述处理完成后 `Monitor Mode` **仍可能显示 `ULM`**，但性能已恢复正常（电脑 A 实测 Ubuntu 安装写入速率 20-45 MB/s）。不要把 `ULM` 当作唯一判据而反复重启——应以**实际吞吐**（磁盘写入速率、编译耗时）是否可接受为准。

两台宿主机都要处理并记录处理结果。基线要求"资源配置相同不代表宿主机性能相同，运行耗时单独记录"，宿主机是否加载 hypervisor 是造成两台耗时差异的最大单一因素，必须登记。

## 地图接口约定

示例地图、试验区域地图和最终项目区域地图都作为独立的地图数据集管理。建图与仿真流程只依赖统一的地图接口，不把某一份测试地图、区域名称或固定路径写入程序和启动配置。

每份地图至少包含以下内容：

- `metadata.yaml`：地图 ID、版本、来源、生成时间、坐标系、单位、分辨率、原点、数据格式和处理参数。
- `map/`：三维点云或后续三维场景模型，以及对应的轨迹和建图工程。
- `config/`：与该地图相关的 GLIM、坐标变换和处理配置；通用算法参数放在环境配置中。
- `checks/`：覆盖范围、实测尺寸、质量检查和已知限制。

后续仿真与导航通过地图数据集路径或地图 ID 加载地图。替换地图时只替换数据集及其元数据，保持加载接口、坐标约定和消息接口不变。当前示例地图仅作为流程验证输入，实际项目区域重新扫描后生成新的地图 ID 和版本。
