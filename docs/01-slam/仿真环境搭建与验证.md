# Gazebo 仿真环境搭建与验证

记录 **GLIM 三维地图 → 2D 导航栅格 → Gazebo Classic 仿真世界 → 小车 + 2D 雷达 + 人流** 这条链路的可行性验证过程、已验参数与踩坑。

**验证结论：这条路走得通。** 用官方 MID-360 示例数据（277 秒城市驾驶）跑通全链路，仿真实时率 **0.97x**，2D 雷达 **9.74 Hz**，人流仿真正常。

> 相关问题条目见 [已知问题与避坑记录](已知问题与避坑记录.md)；本文只收录仿真阶段特有的坑。

---

## 一、技术选型与理由

| 环节 | 选择 | 理由 |
| --- | --- | --- |
| **地图表示** | **2D 占据栅格**（`nav_msgs/OccupancyGrid`） | nav2 的原生输入；**唯一能让"仿真参数"直接搬到"实机部署"的表示** |
| **静态世界** | 栅格 → 轮廓矩形 → SDF box | **与导航图同源**，不会出现"仿真里能过、实机过不去" |
| **仿真器** | **Gazebo Classic 11** | 生态最成熟、插件最全、CPU `ray` 传感器可用 |
| **运行方式** | **headless（只跑 `gzserver`）** | 虚拟机 `SVGA3D` 虚拟 GPU 渲染不了几千个实体 |
| **人流** | 2D 栅格上的排斥模型 → 写回 Gazebo | 2D 栅格上做人群仿真是天然的：墙就是障碍，raycast 就是视线遮挡 |

**明确排除**：三维网格重建（人工清理不可复现、产物进不了物理引擎、虚拟机跑不动）、2.5D 高度图（为室外地形设计）、OctoMap 当世界（体素数量会让 Gazebo 卡死）、Webots（另一套重型引擎）。

## 二、GLIM 输出格式（实测）

### 2.1 目录结构

```
dump/
├── graph.txt                 位姿图
├── 000000/ ... 000176/       177 个子图
│   ├── points_compact.bin        float32 × 3，点坐标
│   ├── normals_compact.bin       float32 × 3，法向量
│   ├── covs_compact.bin          float32 × 6，对称协方差（体积恰为 points 的 2 倍）
│   ├── intensities_compact.bin   float32 × 1，强度
│   ├── data.txt                  文本元数据
│   └── imu_rate.txt
```

**"compact" 指紧凑排列，不是压缩。** 判据：四个文件大小都能被 `12/16/24` 整除，且点数一致。

读取只需一行：

```python
pts = np.fromfile('000000/points_compact.bin', dtype=np.float32).reshape(-1, 3)
```

### 2.4 ⚠️ 点云在子图**局部**坐标系，必须变换

**这是本节最重要的一条。** 判别方法：看各子图**原始点云的质心**。

```
子图     原始质心               T_world_origin 平移
  0   [  4.39, -2.47,  2.44]   [  -0.06,   5.41,  -0.15]
 20   [  5.83,  2.71,  3.07]   [ -84.63,  15.76,  -1.28]
 60   [ -4.10,  0.31,  4.24]   [-242.62,  89.08,  -4.82]
100   [ 20.48,  3.43,  5.89]   [ -58.29, 317.65, -11.16]
176   [  4.19,  5.72,  5.83]   [ -14.43, -24.84, -42.52]
```

**质心全在 ±20 m 内**（各子图围绕自己的局部原点），而**平移列沿轨迹跑到 -242 / +317 m**。两者不相关 → **局部坐标系**。

```python
w = pts @ T[:3, :3].T + T[:3, 3]     # 子图局部 → 世界
```

## 三、地图生成流程

```
GLIM dump
  ↓ ① 读点云 + T_world_origin，变换到世界系
  ↓ ② 计算局部地面参考
  ↓ ③ 高度带过滤，分出"障碍"与"地面（自由）"
  ↓ ④ 投影到 XY，栅格化，阈值二值化
  ↓ ⑤ 沿采集轨迹清理走廊
  ↓ ⑥ 自检：轨迹必须落在自由空间
  ↓ ⑦ 保存 map.pgm + map.yaml
```

### 3.1 ⚠️ 地面参考是关键，且不能用统计分位

**本数据集实测：轨迹的 Z 从 -0.15 单调降到 -42.52 m**，且路线**绕回了起点区域**——同一 XY 上不可能存在相差 40 m 的平行道路，**所以这是垂直漂移，不是真实坡度**。

> **反面教训**：曾用"传感器离地高度稳定在 1.73-2.19 m"推断坡度真实——**这个推理不成立**。局部一致性恰恰是漂移的典型表现（SLAM 局部准、全局飘）。

**因此：绝对 Z 在这份数据上没有全局意义，任何全局高度带都会失效。** 必须逐子图给地面参考。

**采用方法：传感器高度法**

```python
z_ground(i) = T_world_origin[i].z - LIDAR_HEIGHT
```

`LIDAR_HEIGHT` 是**雷达离地安装高度**——本数据集为车顶雷达，取 **1.85 m**；博物馆小车取实车设计值。**这是可测量的物理参数，不是从数据里猜出来的。**

（对比：用"每子图点云 Z 的 5% 分位"作参考，本数据在子图 0 会偏低约 0.35 m，在陡降段偏低 3-5 m，不可用。）

### 3.2 ⚠️ 高度带的上下限都极易设错

**下限（`H_MIN`）设低了 → 路面本身被判定为障碍**

地面参考偏低 0.35 m 时，`H_MIN = 0.3` 会让路面点（`dz ≈ +0.35`）落进障碍带。**后果是整条路变成 3 米高的墙**——机器人被埋在里面，雷达读数全部是 0.3-0.6 m。

**上限（`H_MAX`）设高了 → 头顶障碍盖住路面**

本数据 `H_MAX = 12 m` 时，**树冠**被投影到路面；博物馆里则是**天花板**——整张图变成一片障碍。

**博物馆场景的取值**：`H_MIN = 0.1~0.2`（平地板 + 已知雷达高度，参考准），`H_MAX` **必须低于层高**（如层高 4 m → `H_MAX = 3.5`）。

### 3.3 ⚠️ 分辨率必须匹配点间距

MID-360 角分辨率约 **0.2°**。墙面距雷达 **50 m** 时，相邻两条激光的落点间距：

```
50 m × tan(0.2°) ≈ 0.175 m
```

**若栅格取 0.05 m，相邻点之间隔 3-4 个空格子 → 墙变成散点阵。**

实测：0.05 m 时**开运算删掉 77.6% 的障碍格**（因为全是孤立点）；改到 0.2 m 后降到 **18.0%**。

| 场景 | 建议分辨率 | 理由 |
| --- | --- | --- |
| 室外 / 远距离（50 m+） | **0.2 m** | 点间距 0.175 m |
| 博物馆室内（5-20 m） | **0.05 m** | 点间距 0.02-0.07 m |

### 3.4 ⚠️ 高度带上限不能砍太狠

同理，把立面从地面到屋顶的点**全部投到 XY 上是同一条线**——砍掉高度不会让图更干净，只会让线断掉。

实测：`H_MAX = 4.0` 时只有 22% 的点落在障碍带内，图极其稀疏；放宽到 12.0 后升到 60%。

### 3.5 沿轨迹清理走廊

**逻辑上是硬的：车开过的地方一定能通行。**

```python
# 沿每个子图位姿挖出半径 1.5 m 的走廊
corr[r0:r1, c0:c1] |= (yy*yy + xx*xx) <= R*R
occ &= ~corr
```

作用：清掉"头顶障碍投影到路面"的假墙，**保证轨迹 100% 可行**。

### 3.6 ⚠️ 必须自检：轨迹可行率

**这是整条流程最重要的验收指标。**

> 机器人开过的地方如果在地图上是障碍，这张图一定是错的。

```python
# 对每个子图位姿，检查栅格上是否为障碍
轨迹可行率 = 不在障碍格的轨迹点数 / 总轨迹点数     应 = 100%
```

**这个自检能一次抓出 3.2、3.3 两节的所有参数错误**——本流程早期版本因地面参考偏低，此指标只有 0%（整条路都是墙）。

### 3.7 实测参数演进

| 版本 | 分辨率 | 高度带 | 地面参考 | 障碍格 | 开运算删格 | 轨迹可行率 |
| --- | --- | --- | --- | --- | --- | --- |
| v1 | 0.05 | [0.3, 4.0] | 5% 分位 | 57,602 | **77.6%** ✗ | — |
| v2 | 0.20 | [0.3, 12.0] | 5% 分位 | 72,633 | 18.0% ✓ | — |
| v3 | 0.20 | [0.5, 3.0] | 5% 分位 | 27,585 | — | 85.7% |
| v4 | 0.20 | [0.8, 3.0] | **传感器高度** | 24,615 | — | 93.9% |
| **v5** | **0.20** | **[0.8, 3.0]** | **传感器高度 + 走廊清理** | **23,847** | — | **100%** ✓ |

**v4 → v5 说明**：把 `H_MIN` 从 0.5 提到 0.8 只把可行率从 85.7% 拉到 93.9%，之后到 1.5 都不再变化——**说明剩余的问题不是低矮障碍，而是头顶障碍投影**。**走廊清理才是一刀解决的手段。**

## 四、2D 栅格 → Gazebo 世界

### 4.1 贪心矩形分解

**不能一个格子一个 box**（72,633 个会把 Gazebo 拖死）。

```python
# 逐行扫描，向右扩展成 run，再向下扩展成矩形
used = np.zeros_like(occ, dtype=bool)
for r in range(h):
    c = 0
    while c < w:
        if occ[r,c] and not used[r,c]:
            c2 = c
            while c2+1 < w and occ[r,c2+1] and not used[r,c2+1]: c2 += 1
            r2 = r
            while r2+1 < h and occ[r2+1, c:c2+1].all() and not used[r2+1, c:c2+1].any(): r2 += 1
            used[r:r2+1, c:c2+1] = True
            rects.append((c, r, c2, r2))
            c = c2 + 1
        else:
            c += 1
```

### 4.2 世界分辨率要比导航栅格粗

**世界只需要挡住物理和射线，不需要毫米精度。** 降采样用**最大池化**（有障碍就保留，宁可保守）：

| 世界分辨率 | 矩形数 | world 文件 | gzserver 加载时间 |
| --- | --- | --- | --- |
| 0.2 m（同导航图） | 5,093 | 2.39 MB | **29 秒** |
| **0.4 m** | **2,099** | **0.92 MB** | **约 12 秒** |

**模型数量直接决定加载时间和实时率** —— 见第六节。

### 4.3 SDF 世界骨架

```xml
<sdf version="1.6">
  <world name="museum">
    <plugin name="gazebo_ros_state" filename="libgazebo_ros_state.so"/>
    <include><uri>model://sun</uri></include>
    <include><uri>model://ground_plane</uri></include>
    <physics type="ode">
      <max_step_size>0.004</max_step_size>
      <real_time_update_rate>250</real_time_update_rate>
    </physics>

    <model name="w0"><static>true</static>
      <pose>cx cy 1.5 0 0 0</pose>          <!-- 墙高 3 m，中心在 1.5 -->
      <link name="l">
        <collision name="c"><geometry><box><size>sx sy 3.0</size></box></geometry></collision>
        <visual name="v"><geometry><box><size>sx sy 3.0</size></box></geometry>
          <material><ambient>0.75 0.75 0.72 1</ambient><diffuse>0.75 0.75 0.72 1</diffuse></material>
        </visual>
      </link></model>
    ...
  </world>
</sdf>
```

**2D 抽象消除了 Z 的绝对位置问题**：墙统一从 z=0 立起 3 m，不受地图原 Z 漂移影响。

## 五、机器人模型与传感器

### 5.1 模型结构

```
base_footprint
└── base_link（0.5 × 0.4 × 0.2 长方体）
    ├── left_wheel / right_wheel（连续关节，半径 0.06，轮距 0.40）
    ├── caster（球，半径 0.03）
    └── lidar_link（圆柱，位置 (0.1, 0, 0.15)）
```

### 5.2 插件类型必须放对位置

**这是本阶段最容易搞混的一点**——四种插件类型，放错就报 `detected an incorrect plugin type`。

| 插件 | 类型 | 放在哪 |
| --- | --- | --- |
| `libgazebo_ros_init.so` | **System** | `gzserver -s` 命令行 |
| `libgazebo_ros_factory.so` | **System** | `gzserver -s` 命令行 |
| **`libgazebo_ros_state.so`** | **World** | **world 文件的 `<world>` 内** |
| `libgazebo_ros_diff_drive.so` | Model | URDF 的 `<gazebo>`（模型级） |
| `libgazebo_ros_ray_sensor.so` | Sensor | URDF 的 `<sensor>` 内 |

**查插件类型的通用方法**：

```bash
for f in /opt/ros/humble/lib/libgazebo_ros_*.so; do
  echo "--- $(basename $f)"
  strings "$f" | grep -oE '(System|World|Model|Sensor)Plugin' | sort -u | head -3
done
```

### 5.3 激光雷达配置

```xml
<sensor type="ray" name="lidar">
  <update_rate>10</update_rate>
  <ray>
    <scan><horizontal>
      <samples>180</samples>
      <min_angle>-3.14159265</min_angle>
      <max_angle>3.14159265</max_angle>
    </horizontal></scan>
    <range><min>0.15</min><max>30.0</max></range>
    <noise><type>gaussian</type><mean>0.0</mean><stddev>0.01</stddev></noise>
  </ray>
  <plugin name="lidar_plugin" filename="libgazebo_ros_ray_sensor.so">
    <ros><remapping>~/out:=scan</remapping></ros>
    <output_type>sensor_msgs/LaserScan</output_type>
    <frame_name>lidar_link</frame_name>
  </plugin>
</sensor>
```

**必须用 CPU 的 `ray`，不能用 `gpu_ray`** —— 后者需要 GPU，虚拟机里不可用。**好消息：CPU `ray` 不需要渲染，所以 headless 完全不影响雷达数据。**

## 六、性能：三项决定生死

### 6.1 实测对比

| 配置 | `/scan` 频率 | 实时率 |
| --- | --- | --- |
| 5,093 box + 物理 500 Hz + 雷达 **360** 线 | 2.95-3.08 Hz | **0.30x** ✗ |
| **2,099 box + 物理 250 Hz + 雷达 180 线** | **9.88 Hz** | **0.99x** ✓ |
| 上者 + 12 个行人（5 Hz 更新） | **9.74 Hz** | **0.97x** ✓ |

**三项改动合计提速 3.3 倍：**

| # | 改动 | 效果 |
| --- | --- | --- |
| 1 | 世界模型 5,093 → 2,099 个 | 加载 29s → 12s；物理对象减半 |
| 2 | 物理步长 500 Hz → 250 Hz | 物理计算减半 |
| 3 | 雷达线数 360 → 180 | 射线查询减半 |

**三项缺一不可。** 只改其中一两项达不到 1.0x。

### 6.2 headless 是不传之秘

```bash
# ✅ 这样跑
gzserver --verbose <world> -s libgazebo_ros_init.so -s libgazebo_ros_factory.so

# ❌ 不要起 gzclient
```

**虚拟机是 `SVGA3D` 虚拟 GPU，几千个 box 全渲染会直接卡死。** 看画面用 RViz2。

### 6.3 加载时间正比于模型数

`spawn_entity.py` 默认等待 30 秒。**5,093 个模型时服务在第 29 秒才出现**——正好卡在边界上，导致 spawn 失败并报 `Service /spawn_entity unavailable`。

**必须显式加大超时**：`-timeout 180`。

## 七、人流仿真

### 7.1 设计

```
在 2D 栅格上跑人群模型
   ↓ 每个行人是一个位姿 (x, y, yaw)
   ↓ 通过 /gazebo/set_entity_state 写进 Gazebo
   ↓ 机器人的雷达就打到"人"
```

**这就是为什么先做 2D 栅格是对的**——人群仿真在栅格上几乎是顺手就能加：墙就是障碍，raycast 就是视线遮挡。

### 7.2 最小实现

- **12 个行人**，每个是半径 0.25 m、高 1.7 m 的**静态圆柱**（静态 = 无限质量，机器人撞不动）
- **行为**：朝目标点走 + 互相排斥（近距离斥力）+ 撞墙就换目标
- **更新率 5 Hz**，服务调用 fire-and-forget（不阻塞主循环）
- 只用纯 numpy，**不依赖 ORCA/RVO2 等外部库**

### 7.3 验收

```bash
for i in 1 2 3; do
  ros2 topic echo /scan --once --field ranges 2>/dev/null | md5sum
  sleep 2
done
```

**三次哈希不全相同 = 环境在变 = 人在动、雷达看得见** ✓

**代价**：12 个行人把实时率从 0.99x 拉到 0.97x（降幅 1.4%），可以忽略。

### 7.4 真实化方向（后续）

| 层次 | 方案 |
| --- | --- |
| 基础（已做） | 排斥模型，脚本化目标 |
| 进阶 | **ORCA / RVO2** —— 行人与行人、行人与机器人的双向避让 |
| 高阶 | 真实轨迹数据回放（若有场馆监控数据） |
| 最高 | 按博物馆真实人流模式编排（旅行团、散客、高峰） |

**注意**：**不要用"纯随机移动"**。纯随机既不真实，也会给出错误结论——真实行人**会主动让开机器人**。

## 九、换到博物馆场景要改什么

| 参数 | 现在（室外示例） | 博物馆 | 理由 |
