**交付方**：A 线（电脑 A）
**接收方**：B 线（电脑 B）
**打包日期**：2026-10-13
**基线编号**：`SLAM-TPL-v1`

## 一、这是什么

这是电脑 A 上已经配置完成并验证通过的 Ubuntu 开发环境，按 [虚拟机环境基线](../../docs/01-slam/虚拟机环境基线.md) 打包，用于**部署电脑 B**。

**目的**：电脑 B 直接使用这份环境，不需要从零配置。

这不是为了方便，而是**必需**：A3 阶段的「两机交叉验证」要求两台跑同一份示例数据、比对建图结果。如果两台的软件版本有任何差异，差异就无法归因——分不清是算法问题还是环境问题。用同一个镜像部署是消除这个变量的唯一可靠办法。

## 五、部署步骤

### 第 0 步（最重要）：先处理 B 的宿主机

**这一步不做，后面全部白费。**

宿主机如果加载了 Windows 虚拟机监控程序（Hyper-V / VBS），VMware 会退到用户态监控器 `Monitor Mode: ULM`，CPU 与磁盘 I/O 慢一个数量级。电脑 A 就因此出现过 Ubuntu 安装器长时间无响应、安装一字节都没写入的情况。

**判断方法**：管理员终端执行

```
bcdedit
```

在输出里找 `hypervisorlaunchtype`。**没有这一行、或显示 `Auto`，就说明还没处理。**

**处理步骤**（按顺序，每步后重启）：

1. Windows 设置 → 系统 → 高级 → 虚拟工作区 → 关闭「**虚拟机平台**」和「**Windows 虚拟机监控程序平台**」
2. 管理员终端：`bcdedit /set hypervisorlaunchtype off`
3. 注册表关闭 VBS：把 `DeviceGuard\EnableVirtualizationBasedSecurity` 和 `DeviceGuard\Scenarios\SystemGuard\Enabled` 都改成 `0`
4. 重启

> **代价**：WSL2 和 Docker Desktop（WSL2 后端）会失效。需要用 Docker 时，在 Ubuntu 虚拟机里装（Linux 里跑 Docker 是原生支持，比 Windows 上更标准）。

> **注意**：处理完之后 `Monitor Mode` **仍可能显示 `ULM`**，但性能已经正常（电脑 A 实测磁盘写入 20-45 MB/s）。**不要以 `ULM` 为唯一判据反复重启**，以实际速度为准。

**详细说明见** [虚拟机环境基线](../../docs/01-slam/虚拟机环境基线.md) 的「宿主机前提」一节。

### 第 1 步：复制到 B 机

把整个 `Slam-B` 文件夹复制到 B 机上。

- **必须整个文件夹一起复制**，9 个文件一个都不能少——增量盘依赖基础盘，缺一个虚拟机就打不开
- 建议放到 `E:\大创文件\VMs\` 下（与 A 机布局一致）
- 21.5 GB，U 盘请用 USB 3.0（虚拟机已配 XHCI 控制器，B 机若走 U 盘传输会快很多）
- **复制完成后用 `校验值.txt` 核对**，确认传输没出错

### 第 2 步：打开虚拟机

VMware Workstation → **文件 → 打开** → 选 `Slam-B\Ubuntu22.04-GLIM.vmx`

> **弹出「移动还是复制」时必须选「我已复制该虚拟机」。**
>
> 选错（选「我已移动」）会导致 B 的 MAC 地址和 UUID 与 A **完全相同**，两台同时联网时直接冲突。

### 第 3 步：改计算机名

B 机的主机名不能和 A 相同——ROS 2 的 DDS 靠主机名做节点发现，两台同名会互相抢占。

```bash
sudo hostnamectl set-hostname Slam-b
```

改完重启生效。**用户名 `wang` 保持不动。**

### 第 4 步：重新生成 machine-id

镜像复制后 `/etc/machine-id` 与 A 相同，同网段可能引起 DHCP 分配冲突：

```bash
sudo rm /etc/machine-id
sudo systemd-machine-id-setup
cat /etc/machine-id
```

输出应与 A 机不同。

### 第 5 步：配置网卡 2 的桥接

虚拟机设置 → 网络适配器 2 → **桥接模式** → 选择 B 宿主机上接雷达的那块物理网卡。

（A 机这一项也还没最终确定，等接 MID-360 时两台一起定，并记录到基线文档的"部署参数"里。）

### 第 6 步：处理 CD/DVD 的失效路径

`.vmx` 里的光驱指向一个相对路径 `..\ubuntu-22.04.5-desktop-amd64.iso`。如果 B 机对应位置没有这个 ISO，VMware 可能提示找不到文件。

**处理**：虚拟机设置 → CD/DVD → 取消勾选「启动时连接」即可（系统已装好，用不到光驱）。

### 第 7 步：拍同名快照

开机确认一切正常后，拍摄一个快照，名称与 A 机对齐（A 机的两层快照已随包带入，这一步是补一个"B 机部署完成"的基准点，命名双方约定一致即可）。

## 六、验证清单

开机后逐条执行，**全部通过才算部署成功**：

```bash
# 1) 主机名已改
hostname

# 2) 环境变量（应输出 4 行：2 个 source + 2 个 export）
grep -n "ros/humble\|ws_livox\|RMW_IMPLEMENTATION\|ROS_DOMAIN_ID" ~/.bashrc

# 3) ROS 2
source /opt/ros/humble/setup.bash
echo $ROS_DISTRO            # 期望 humble

# 4) GLIM
ros2 pkg list | grep -i glim        # 期望 glim、glim_ros 两个包
ros2 run glim_ros offline_viewer    # 期望弹出交互式查看器窗口

# 5) RViz2（同时验证 3D 加速）
rviz2                                # 期望窗口正常、网格渲染正常

# 6) Livox 驱动
source ~/ws_livox/install/setup.bash
ros2 pkg executables livox_ros_driver2    # 期望 livox_ros_driver2_node
ldd ~/ws_livox/install/livox_ros_driver2/lib/liblivox_ros_driver2.so | grep -i livox
                                          # 期望 liblivox_lidar_sdk_shared.so 正常解析

# 7) 目录布局
find ~/slam -type d         # 期望 6 个目录
```

**任何一条不符，先不要继续往下做**，把输出发回 A 线排查。

## 七、已知问题（来自 A 机的部署经历）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 虚拟机卡到无法使用 | 宿主机 Hyper-V/VBS 加载 | 见第 0 步 |
| `EFI ... CDROM Drive ... No Media`，无法引导 | 误点「安装 VMware Tools」会顶掉光驱 | 不要点该菜单项；VMware Tools 用 `sudo apt install open-vm-tools open-vm-tools-desktop` |
| `ros2` 命令找不到 | 环境变量没生效 | `source /opt/ros/humble/setup.bash`，确认 `~/.bashrc` 有那一行 |
| `liblivox_lidar_sdk_shared.so: not found` | SDK 未装或未 `ldconfig` | 检查 `/usr/local/lib/` 下是否有该文件，然后 `sudo ldconfig` |

## 八、B 线接下来做什么

环境就绪后，B 线的任务是 [实机建图 TODO](../../docs/01-slam/实机建图TODO.md)：接入 MID-360、试录、人工扫描、离线建图、地图交付。

**部署完成后先按本文第六节的验证清单逐条自查**，全部通过再接雷达。

**关于"两机交叉验证"**：本交付包由同一镜像生成，两台软件版本、配置与路径**逐字节相同**，因此**不需要再用示例数据做两机交叉验证**。原基线中的该要求写在"两台各自手工配置"的前提下，该前提已不成立。理由见 [虚拟机环境基线](../../docs/01-slam/虚拟机环境基线.md) 的「环境一致性如何保证」。

仍需要注意的是：**「软件环境相同」不等于「运行结果相同」**——多线程优化本身存在非确定性，数值比对一律按预先记录的容差进行。另外两台宿主机性能差异导致耗时不同属正常，按基线要求单独记录。
